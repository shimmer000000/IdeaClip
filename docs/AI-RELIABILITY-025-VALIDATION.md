# 0.2.5 单篇AI商业模式分析可靠性验收

日期：2026-11-09。基线`b463167f622e6eee5347c7049dcec48b9586d9f5`。本文件与0.2.5代码同次提交，最终SHA以文件所在提交为准。

## 证据与问题边界

本轮重点为`analysis.html`单篇笔记，不是深度研究向导。沿用0.2.4的响应→JSON→Schema→证据→保存诊断。历史schema/validation错误没有原始响应，不能推断必然缺栏、预算不足、引用错误或DeepSeek不支持协议；没有恢复或改写旧失败报告。

确切发现：

1. 请求计时器直到整个run结束才释放，完整响应已收到后仍覆盖本地usage写入及后续授权复查。用Mock即时响应、本地usage写入延迟1100ms、请求超时1000ms复现：保留旧计时逻辑的定向回放失败为timeout；恢复修复后同用例成功保存。计时器现于完整transport返回时结束；传输中的超时、用户取消、总开关和来源版本复查继续有效。
2. 模型有效、仅本地保存失败时，重试save成功虽写reportSaved=true，但aiUsage仍留ai_report_save错误。现在只清除该次已恢复保存的errorCode/errorStage；原预留、usage和诊断历史保留，不改其他失败或历史费用。此修复有Mock前后元数据与请求次数断言。
3. 15栏原提示只有Schema和“每节1～8条”，没有完整结构示例与优先单条的输出指导。新增示例及精简策略是可靠性设计改进，尚无真实模型成功率对比证据，不声称已证明它是历史失败根因。
4. 配置允许8192输出而业务模板上限4096，实际请求取较小值；这是原有安全预算规则，本轮保持，但页面现在解释设置/模板/实际三值及低预算风险，避免误解为实际一定发送8192。

## 协议核对与实现

只访问官方公开文档，无密钥、无模型调用：

- [DeepSeek JSON Output](https://api-docs.deepseek.com/guides/json_mode/)：支持response_format.type=json_object，要求提示JSON及示例，并合理设置max_tokens；stop仍可能出现空白content。保留现有空内容诊断和不自动重试策略。
- [Chat Completions](https://api-docs.deepseek.com/api/create-chat-completion/)：官方端点、非流式JSON、max_tokens与thinking.type=disabled仍符合现有适配。本轮不改用未经验证的json_schema/strict协议、不联网探测模型、不新增工具调用或服务商。

商业模板版本1.0.1、报告schemaVersion仍为1。提示列出所有15个键及有效JSON结构，要求每栏优先1条、有价值且简短；1～8条合法范围不变。较低上限建议更短文字，先保证结构完整；信息不足用hypothesis/inference与null证据，不填空数组或伪造fact。完整结构示例通过实际Schema单元验证，但示例不是分析内容，程序不会拿它补齐模型输出。

fact仍仅为来源主张，evidence必须与实际发送的原文连续逐字相符；提示明确输入JSON解码与输出转义、保留换行/引号/Unicode，不得引用模板说明或示例。匹配器没有模糊匹配、归一化、翻译、裁剪或自动替换引文。

输出预算仍取设置和模板上限最小值，业务模板4096上限不变、默认配置不提高。2048为经验建议，不是模型专属Token计算或完整输出保证；低于建议时提示风险，不擅自改配置。输入Token保守估算包含新增提示/示例，费用仍在当次完整预览中确认。

已存内置1.0.0启停记录，只有与原应用定义完全相同才只读映射到1.0.1；保留enabled=false。旧数据库行、历史报告和模板快照不改写；旧自动发送绑定版本/签名不再匹配，须人工重新授权。不接受篡改的旧模板，不将JSON文件或升级视为发送授权。
