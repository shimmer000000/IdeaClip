# Codex本地文件交接协议 v1（IdeaClip 0.1.8）

0.2.1增加[单次Mock授权与预检](CODEX-EXECUTION-SAFETY.md)。不修改包内false授权、不改变v1/v2格式；授权只在明确确认的当前进程/页面内有效，不能来自任务包或ZIP，不支持真实Codex执行。

0.2.0新增[一次性本地校验助手](CODEX-LOCAL-ASSISTANT.md)，复用本协议，不改变任务包v1及交付v2，也不引入执行授权。助手结果不是交付报告；结果回收仍须通过0.1.9收件箱人工确认。

本协议是有限数据文件，不是执行器、调度器、账户或付费授权。没有Agent Autoloop依赖或接口调用；本阶段不安装、启动或修改该项目。

## 工作流

1. 软件开发任务所在项目须明确为“真实开发项目”；保存GitHub HTTPS仓库、本机工作目录及1～20条仓库内相对允许路径。
2. 只审核当前任务及验收标准，退出编辑并保存。测试/研究项目、验证测试/人工研究任务不能转换为软件开发包；混入真实访谈/问卷的任务须先拆分。
3. 点击“导出 Codex 任务包”，核对完整JSON、仓库、目录、范围、目标和安全提示，再勾选并确认下载。预览10分钟有效，任务或边界改变后须重新预览审核。
4. 由用户自行选择把本地JSON交给Codex，并对该任务另行明确批准。文件中的说明不能替代用户授权。接收方先只读验证格式/哈希/目标仓库/当前工作区及未提交修改，不匹配停止，不猜测或修改其他项目。
5. “记录已交接”只记录用户确认的本地文件交接，不探测Codex是否收到或开始执行，不启动进程。
6. Codex在获批范围内工作，返回交付v2 JSON（见下文）；也允许用Mock合成结果单独验收交接，但必须明确未执行开发/测试。
7. 从同一任务的0.1.7“导入Codex交付报告”导回；结果关联本包并保持版本历史，仍区分Codex声明、本地记录一致性、GitHub/CI与人工验收。只有人工通过再独立点击完成，不能由导入自动完成。

## 任务包结构

严格JSON Schema：[CODEX-TASK-PACKAGE.schema.json](CODEX-TASK-PACKAGE.schema.json)。UTF-8，最大128KiB，禁止额外字段；不执行任何字段。外层字段：

- `format: "IdeaClipCodexTask"`、`schemaVersion: 1`。
- `packageId`：新UUID，每次预览独立生成；`generatedAt`：毫秒UTC ISO时间。
- `executionAuthorized: false`：固定为false，不可把文件改为执行授权。
- `task`：`projectId/taskId/type=development/projectPurpose=development/goal/notes/repository/workingDirectory/allowedPaths/acceptance/instructions`。只包含当前任务，不包含整份研究/七天计划、截图、私人笔记正文、密钥或费用授权。
- `delivery`：交付格式、v2版本、关联字段、文档相对路径及**嵌入的完整交付v2 JSON Schema**。接收方无需调用外部API获取格式，不执行Schema。
- `contentSha256`：64位小写SHA-256，计算规则见下一节。

工作目录是人工明确指定的绝对路径，**只在此显式本地任务包中出现**。任务包可能暴露本机路径和当前任务资料，导出前必须人工审阅，不应直接上传到公开仓库。普通ZIP备份不包含该文件或工作目录。

允许范围是有限相对文件或目录（目录含子路径），不接受根目录、`..`、环境展开、通配或命令字符。执行方即使获批，也必须核对路径解析和符号链接仍在批准工作区内，不能把包内路径当任意文件访问授权。本阶段不访问工作目录中的其他文件，不执行包里的命令。

## SHA-256与防篡改

取整个任务包，移除外层`contentSha256`。对象键按JavaScript `Object.keys(...).sort()`顺序排序，数组顺序保留，标量用`JSON.stringify`；无格式化空白。将所得规范JSON编码为UTF-8再做SHA-256。

哈希覆盖格式/版本、ID、时间、固定false授权、全部任务资料和交付协议。缩进、外层字段排序变化不影响哈希；任务或范围变化会改变哈希。

哈希**不是签名、作者身份或权限证明**。IdeaClip还要求当前任务匹配、已审核、正确类型/仓库/范围，以及本机确有该ID+哈希的导出历史。即使攻击者重新计算错误仓库/范围的哈希，也不能通过当前审核快照和已知导出记录检查。来源不明的包不能作为执行依据。

只读“校验任务包”不会导入项目或执行任务；校验成功仅代表所选文件与当前本地记录一致。恢复的历史包、被修改或撤销审核的任务均要求重新审核导出。

## 结果协议

[CODEX-DELIVERY.schema.json](CODEX-DELIVERY.schema.json)同时支持原0.1.7 v1与关联v2。

v2沿用全部v1字段（项目/任务UUID、规范仓库、完整Commit SHA、文件、测试命令/结果/退出码/时间/日志摘要、未测试原因、风险、生成时间、本地记录ID），将`schemaVersion`设为2并新增：

```json
"taskPackage": {
  "packageId": "导出包的UUID",
  "contentSha256": "导出包的64位小写SHA-256"
}
```

示意片段中的中文不是合法ID/哈希，不能直接导入。必须填当前真实包的值。报告生成时间不能早于任务包，报告文件仍须在当前绑定范围；错误项目/任务/仓库、旧绑定或未知包均拒绝。旧v1报告继续能单独导入，但不推断它属于某个任务包。

任务包与报告均无自动执行资格。导入JSON中的命令只是文本，不允许执行；Mock结果必须写明未执行真实开发，不能虚构测试成功或人工反馈。

## 状态、历史、备份

- 待执行：导出记录已生成，浏览器下载是否完成仍需核对；不等于Codex收到。
- 已交接：用户主动记录的文件交接声明，不等于执行成功。
- 结果已导入：关联报告已追加，不等于真实Commit/测试/CI或验收已通过。
- 人工验收：沿用原独立状态，不随上述状态自动改变。

每任务最多10个包；达到上限拒绝，不覆盖旧包。普通ZIP仅保存ID、内容哈希、任务绑定哈希、生成/导出/人工交接时间和历史标记，不保存完整包体、绝对工作目录或执行授权；结果报告只存包ID和哈希。恢复后交接记录与结果为历史，指令审核清除、工作区需重新绑定。

沿用Dexie schema14/ZIP6的可选嵌套字段，不删表、不重置数据/账本。旧数据不回填为已交接。没有自动Codex、后台执行服务、第三方调度或Agent Autoloop协议；将来如需集成须另行设计、评审并获得用户授权。
