# 0.1.3 GitHub 开发任务关联与验收管理

日期：2026-11-08。基线：0a04179c5cf4e0d18f22d507494f61164420af3b（0.1.2）。仅修改IdeaClip源码；不修改其他项目、服务器、SSH出口、网络设置或费用账本。

## 实现范围

任务增加可选`github`（仓库、Issue编号/链接、PR编号/链接、Commit SHA/链接、linkedAt）、`codexSummary`和`acceptanceReview`（state、notes、tests）。GitHub信息在任务编辑中新增/修改/删除，看板和列表显示格式校验状态、对应链接、关联时间及独立人工验收状态。优先复用项目workspace中的合法GitHub仓库，开发任务存在两处仓库时必须一致。没有关联的旧任务、测试或人工研究仍可保存与验收。

只接受固定github.com HTTPS仓库路径，拒绝用户凭据、查询/片段、端口、伪装域名、其他站点、路径跳转和空白。Issue/PR编号须正整数且在JS安全整数范围；链接类型和仓库必须一致。Commit SHA为7～40位十六进制，编号或SHA与链接同时提供须一致，不用前缀猜测匹配。短SHA只通过格式检查，不证明唯一或真实存在。规范化只补齐同一引用的编号/链接，不向GitHub发送请求。保存关联时记录本机时间，修改引用后更新关联时间。

所有展示为React纯文本及经过校验的主动链接（noopener/noreferrer），不渲染输入HTML，不执行链接内容。界面只说“格式已核对；远程状态未验证”；不查询Issue关闭、PR合并或Commit存在状态，也不自动创建、关闭、合并、推送或请求AI。

## 人工验收与完成门禁

1. 先保存当前任务输入和交付（可手动录入Commit或PR及摘要）。
2. 再编辑，选择待开发/待验收/验收通过/验收失败。保存通过或失败须填写验收说明与测试结果，并勾选本次人工确认。未测试项目需明确注明，应用不能替用户判断测试是否真实通过。
3. 保存验收通过不会改变待处理/进行中/已完成看板状态。只有原已保存通过，才能独立点击卡片的“人工验收通过，设为已完成”。事务再次检查版本、原通过结论和本任务资料，不能通过普通状态编辑或同一保存跳过步骤。
4. 修改任务内容、GitHub引用、开发结果或执行边界，使原指令审核与验收结论失效，回到待开发或待验收。已完成任务先手动改为待处理/进行中，再改输入或交付/撤销通过。原有无新验收字段的已完成历史原样保留，不自动回填或清空。
5. “可复制指令”审核与人工验收确认独立。改动任务资料取消确认，仅勾选指令审核不会意外清除已经勾选的人工确认。保存失败保留输入，过期窗口拒绝覆盖。

Codex指令仍只含当前任务。新增目标仓库及已关联Issue，沿用本机绝对目录、允许修改的相对范围、本任务验收和禁止覆盖未提交修改/强推；开发交付要求完整Commit SHA/链接和适用PR链接，无PR须说明。复制不执行命令，不自动创建仓库、Issue、PR，不授予推送或发布权限。

## 数据、迁移与备份

可选字段嵌套在原projects表记录中，不新增表/索引，不要求Dexie版本迁移，不重写旧记录。沿用revision冲突检查和单项目事务，保留笔记、截图、研究、来源、报告、项目历史、配置和费用记录。

ZIP v6/schema14保持不变，扩展白名单保留上述业务字段。所有链接重新严格校验，摘要/验收文字仍经过现有凭据脱敏。未知配置字段不导出，本机workspace（含绝对路径和修改范围）不导出；带GitHub引用或验收记录的任务恢复时`reviewed=false`，仅保留人工验收记录作为历史业务信息，不构成复制/执行授权。恢复后开发指令仍须绑定workspace并重新审核。没有新增字段的旧ZIP、项目和任务继续兼容。
